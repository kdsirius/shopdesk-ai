## 环境事实（历史）

- 2026-11-17 用户确认 MongoDB 已部署在虚拟机 `192.168.150.120:27017`：docker-compose 的 `mongo` 服务，容器 `my-mongo`，镜像 `mongo:7.0`，数据目录 `/mongo-data`，root 用户 `admin`，已启用密码。密码只存在用户本地配置，本记录、教程和日志均不记录。
- 同日从 Windows 对 `19530`、`27017` 做过纯 TCP 连通检查，均可达；没有使用账号密码连接 MongoDB，该记录不代表服务在后续会话仍在线。
- 只读查询确认 `kb_item_names` 当时只有 1 条记录：`file_title` 为 `万用表RS-12的使用`，`item_name` 为 `RS PRO RS-12 数字万用表`。
- 混合检索的评分不是原始余弦：实测拆分得到 `0.8 × (1 + cos) / 2 + 0.2 × (0.5 + atan(IP) / π)`，与服务端返回值逐项吻合。本环境服务端 2.5.5 下 `norm_score` 取 `True` 或 `False` 返回的评分相同。
- 真实 BGE-M3 加 Milvus 只读标定的参考评分：完整名称约 0.92，`RS-12 数字万用表` 约 0.88，`RS-12 万用表` 约 0.85（略低于阈值），`RS-12` 约 0.76，`万用表` 约 0.77，`手机` 约 0.67，`烫金机` 约 0.63，`iPhone 15` 约 0.53，`示波器` 约 0.55。库里只有一个产品时，大多数像产品名的词都落在候选区间，只有明显无关的名称才小于 0.6。
- 稀疏检索在完全没有重叠词时可能不返回任何命中（例如 `iPhone 15`），混合检索仍返回 Dense 的命中。

## 版本与资料分歧保留

- 参考的 `get_recent_messages` 先升序再 `limit`，取到的是最早的几条而不是最近的几条；教程改为倒序取最新再翻转，并以 `_id` 兜底，避免 Windows 时钟刻度粗时同刻写入的消息顺序不稳。
- 参考的 `save_chat_message` 更新时重写 `ts`，第 8 步更新用户消息后，用户消息会排在先保存的助手回答之后；教程更新时不写 `ts`。
- 参考用 `list(set())` 去重，会打乱候选顺序，追问取前 3 个可能漏掉最高分；教程用 `dict.fromkeys`。
- 参考在导入模块时连接 MongoDB；教程改为首次使用时连接，与 `get_milvus_client()` 同一写法，并设置 5 秒服务器选择超时。
- 参考用 JSON 模式取结果；教程沿用第 6 节已验证的客户端写法，不开 JSON 模式，解析时取第一个 `{` 到最后一个 `}`，并检查返回形状。
- 参考的单个名称检索失败只记日志，最终会被判成“未找到相关产品”；教程保留这一取舍，并在失败表里提醒这不算分支 C 通过。
- 参考的 `run()` 支持流式输出，本节不需要，没有写入。
