## 首轮发现的问题（历史，修订结果见文末）

### 1. 主体节点 `process()` 缺少第 6 步调用

位置：`src/shopkeeper_brain/processor/import_process/nodes/node_item_name_recognition.py`，第 36—40 行附近。

当前 `process()` 在第 5 步生成名称双向量、写入两个状态字段后直接记录完成并返回，未调用 `_step_6_save_to_milvus()`。AST 对当前真实方法的调用核对确认保存调用数量为 0。

这次用户学习期入口成功，是因为 `node_import_milvus.py` 第 244 行直接调用了主体第 6 步。该入口绕过了主体节点 `process()`，所以不能证明正式节点调用时也会保存主体名称。未来运行主体节点实例时，会生成名称向量却没有名称集合记录。

修订方式：在两个名称向量状态赋值之后、完成日志之前，调用 `_step_6_save_to_milvus(file_title, item_name, dense_vector, sparse_vector)`；不改原有识别或向量生成算法。

本轮未为检查接线重复调用远程 LLM 或 BGE-M3；静态接线核对和真实入库验证分开记录。

### 2. 主体保存的插入结果判断括号位置错误

位置：同文件第 172 行。

当前代码把比较表达式放在了 `result.get()` 的参数里。`"insert_count" != 1` 恒为真，因此实际取的是 `result.get(True)`，正常 SDK 字典没有这个布尔键，得到 `None`，无法触发数量异常。

已抽取真实源码的条件表达式运行核对：成功结果、零条结果、主键列表缺失和计数不符四组字典均得到 `None`。这项检查证明 Python 判断表达式失效，不是模拟数据库或伪造真实 Milvus 写入结果。

修订方式：比较 `result.get("insert_count")` 的返回值，再与 `len(inserted_ids) != 1` 做逻辑或运算。

### 3. 主体保存的异常捕获仅包住 `insert()`

位置：同文件第 152—158 行。

`get_milvus_client()`、`has_collection()`、集合创建和 `delete()` 位于 `try` 外。学习入口直接调用该方法，前述操作失败时会直接暴露 SDK 异常，不能通过现有 `except` 转换为带节点上下文的 `MilvusError`。

本轮只在副本配置中将实验主体集合名改为带连字符的非法名称。真实 Milvus 的 `has_collection()` 返回 `MilvusException(code=1100)`；捕获结果确认为 SDK 异常、无 `node_name`，未进入主体方法中的包装逻辑。没有修改真实服务或用户集合。

修订方式：将现有 `try` 的范围前移到获取客户端之前，统一覆盖连接、集合检查/创建、删除和插入；保留现有项目异常分支与 `raise ... from exc`。
